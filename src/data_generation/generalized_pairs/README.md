# 팀원 2 · 일반화 태그 질문과 SQL

저장소 루트에서 Python 3.10 이상으로 실행한다. 생성 건수(`--count`)와 출력 경로(`--output`)는 필수 CLI 옵션이다. seed(`--seed`, 기본값 0)와 원본 SQL당 질문 상한(`--max-questions-per-sql`, 기본값 자동)도 CLI에서 지정한다. 유형별 비율은 [sql_types.json](sql_types.json)에서만 읽는다. v1 확인용 파일은 seed 42로 만든 질문·SQL 쌍 1,000건이다.

```shell
python src/data_generation/generalized_pairs/generate.py --count 1000 --seed 42 --max-questions-per-sql 3 --output data/v1/generalized_pairs.json
python -m unittest discover -s tests -v
```

`--count`는 파일에 기록할 **질문·SQL 쌍의 총수**다. 위 명령은 원본 SQL 하나에 질문을 최대 3개 배정한다. 상한을 생략하면 원본이 적은 유형에는 최대 64개까지 서로 다른 표현을 쓸 수 있다.

저장소에는 1,000건 표본을 포함한다. 대용량 로컬 생성 결과는 예를 들어 `--output data/v1/generated/generalized_pairs.json`에 저장하면 Git이 제외한다. 원본 SQL 조합을 중복 없이 순회하고 한 레코드씩 JSON 파일에 기록하므로 50만 건을 넘어도 전체 결과를 메모리에 올릴 필요가 없다. 요청량이 현재 표현 조합 수를 넘으면 가능한 건수를 알려준다. 파일은 쓰기가 끝난 뒤 지정한 경로로 교체된다.

## SQL 유형별 비율 설정

생성기는 기본으로 같은 폴더의 [sql_types.json](sql_types.json)을 읽는다. 이 파일을 직접 편집하거나 복사한 뒤 `--sql-types 경로`로 지정한다. [mappings.json](mappings.json)은 계속 질문 표현을 담당한다.

- `family_percent`는 전체 **질문·SQL 레코드 수**에서 각 대분류가 차지하는 백분율이다. 기본값은 일반 조회 50%, 단순 집계 25%, 그룹 조회와 스칼라 서브쿼리 각각 12.5%다. 숫자로 지정하고 남은 몫은 `null`인 대분류가 균등하게 나눈다. 생략한 대분류는 0이다. `null`이 없으면 합계는 100이어야 한다.
- `subtype_percent`의 숫자는 **해당 대분류 안에서의 백분율**이다. 0은 제외, `null` 또는 생략은 남은 비율의 자동 배분을 뜻한다. 한 대분류에서 숫자의 합이 100이면 나머지 세부 유형은 나오지 않는다.
- `example_weights`는 유형 안에서 일반 레코드(`ordinary`)와 대조 레코드(`contrast`, 양쪽 합계)의 상대 가중치다. 기본값은 8과 1이다. 지정한 세부 비율 안에서 짝을 만들 수 있는 만큼 배정하고 나머지는 일반 레코드로 채운다. 대조 전용 설정에서는 두 유형의 건수와 짝의 양쪽이 맞아야 한다.

일반 조회의 56개 세부 비율을 모두 숫자로 지정했다. 일반 조회 500건 안에서 조건 0개는 60건, 1개는 355건, 2개는 55건, 3개는 30건이다. 정렬과 수량 제한이 없는 단일 조건 조회는 180건이며, 등호는 40건, 초과와 미만은 각각 25건이다. 나머지 세 대분류 안의 세부 비율은 자동 배분한다.

**50만 건 규모**에서는 [sql_types_large.json](sql_types_large.json)을 `--sql-types`로 지정하고 원본당 질문 상한은 자동으로 둔다. 두 설정은 대분류와 일반 조회의 조건 수별 비율이 같다. 대용량 설정은 원본 수가 적은 단일 조건 조회에서 정렬이나 `LIMIT`이 있는 변형으로 일부 비율을 옮긴다. 50만 건의 할당량은 일반 조회 25만 건, 그중 단일 조건 177,500건, 그중 정렬·수량 제한이 없는 조회 2,500건이다. 일반 조회에서 만들 수 있는 순위 대조쌍 수를 고려해 일반·대조 가중치를 17:3으로 잡았다. seed 42에서 계산한 대조 레코드는 전체의 약 11.14%다.

직접 비율을 지정하려면 아래 예시를 `my_sql_types.json`으로 저장한다. 이 설정으로 1,000건을 생성하면 일반 조회는 400건이고, 그중 정렬·수량 제한 없이 `WHERE 컬럼 > 값` 하나만 있는 질문은 40건이다.

```json
{
  "family_percent": {"rows": 40, "aggregate": 20, "group": 20, "scalar": 20},
  "example_weights": {"ordinary": 8, "contrast": 1},
  "subtype_percent": {"rows": {"where1:>/plain": 10}}
}
```

```shell
python src/data_generation/generalized_pairs/generate.py --sql-types my_sql_types.json --count 1000 --seed 42 --output data/v1/custom_pairs.json
```

기본 JSON에는 653개 키가 모두 들어 있다. `plain`, `order`, `limit`, `order_limit`은 각각 정렬·수량 제한 없음, 정렬만, 수량 제한만, 둘 다를 뜻한다.

| 대분류 | 세부 유형 수 | 키 예시 | 의미 |
| --- | ---: | --- | --- |
| `rows` | 56 | `where2:OR/order` | 두 조건을 OR로 잇고 정렬 |
| `aggregate` | 15 | `SUM/where1` | 행 필터 하나를 적용한 합계 |
| `group` | 420 | `COUNT/where0/having:>=/order_limit` | 행 필터 없이 그룹별 개수를 세고 HAVING·정렬·수량 제한 적용 |
| `scalar` | 162 | `AVG/>/inner1/outer0` | 안쪽 필터 하나로 구한 평균 초과, 바깥 추가 필터 없음 |

대분류나 세부 유형의 비율을 숫자로 지정하면 요청 건수를 기준으로 정수 할당량을 계산한다. 소수점 아래가 큰 유형부터 남은 레코드를 한 건씩 배정한다. 같은 건수·설정·seed는 같은 결과를 내며, 건수를 바꾸면 할당량과 ID 배정도 달라질 수 있다. 필요한 경우 자동 모드는 원본당 최대 64개까지 서로 다른 표현을 사용한다. 명시한 `--max-questions-per-sql`은 항상 우선한다. 예를 들어 `where1:>/plain`은 서로 다른 SQL이 9개이므로 상한 3에서는 최대 27건이다. 고정한 할당량을 채울 수 없으면 생성기가 해당 유형과 함께 오류를 반환하고 기존 출력 파일을 보존한다.

## 원본 SQL에서 질문을 만드는 과정

1. 생성기는 일반 조회, 집계, 그룹 조회, 스칼라 서브쿼리를 번갈아 선택한다. 일반 조회와 그룹 조회에서는 먼저 `WHERE` 조건 수, `ORDER BY` 유무, `LIMIT` 유무의 조합을 고른다. 집계는 행 조건 수를, 서브쿼리는 바깥쪽과 안쪽의 행 조건 수를 각각 고른다. 각 유형에서 가능한 조합을 seed로 섞어 한 바퀴에 한 번씩 방문하고, 그 안에서 컬럼·연산자·정렬 방향·건수를 정해 원본 SQL을 하나 뽑는다. 한 조합의 SQL을 모두 사용하면 남은 조합으로 계속한다.
2. `--seed`(기본값 0)와 완성된 원본 SQL로 질문 선택용 난수 생성기를 따로 초기화한다. 일반 원본의 첫 질문은 태그를 한 단어로 세어 짧은 틀과 하위 표현을 고르고, 다음 질문부터는 섞어 둔 틀과 표현을 사용한다. 길이가 같은 후보는 seed로 순서를 정한다. 원본당 상한이 틀 수보다 크면 표현을 바꿔 이어 가고 완성된 질문의 중복은 건너뛴다. 표현을 추가할 때는 소문자 자리표시자와 첫 컬럼 등장 순서를 유지한다.
3. 처음 고른 SQL이 원본 1번, 다음 SQL이 원본 2번이다. 첫 원본의 첫 질문 ID는 `1.1`이다. 같은 설정·건수·seed·상한으로 실행하면 순서와 질문을 재현할 수 있다. 총건수를 바꾸면 유형별 할당량과 원본 번호가 달라질 수 있다.

## 의도별 질문과 학습용 대조쌍

`mappings.json`의 `intent`는 해당 SQL에서만 쓸 수 있는 표현을 담는다. 전체·그룹별 `COUNT(*)`는 `how many`처럼 개수를 직접 묻는 질문을, 스칼라 `AVG`는 어떤 행들의 평균과 비교하는지 명시한 질문을 기존 질문 틀과 함께 사용한다. `ORDER BY`와 `LIMIT`이 함께 있으면 상위·하위 N개를 한 번에 요청하거나 정렬과 수량을 따로 말할 수 있다. 보조 정렬 키가 있으면 동점 처리 기준도 질문에 넣는다.

기본 파일은 일반 레코드 8건당 대조 레코드 1건을 목표로 한다. 두 대조 원본은 연달아 나오며 같은 질문 번호끼리 짝이 된다. seed 42, 원본당 최대 3개로 생성한 v1 표본은 원본 SQL 360개, 질문 1,000건이며 그중 112건이 아래 56쌍을 이룬다.

| 대조 유형 | 달라지는 질문 단서 | 달라지는 SQL | 질문 대조쌍 | 예시 ID |
| --- | --- | --- | ---: | --- |
| `rank_direction` | 가장 높은 값부터 / 가장 낮은 값부터 | 같은 키·건수에서 `DESC` / `ASC` | 28 | `4.1` ↔ `5.1` |
| `average_scope` | 테이블 전체의 평균 / 같은 조건을 만족하는 행의 평균 | 바깥 필터는 같고 `AVG` 서브쿼리 안의 `WHERE` 유무가 바뀜 | 7 | `25.1` ↔ `26.1` |
| `boundary` | 초과 / 이상, 미만 / 이하 | `>` / `>=`, `<` / `<=` | 14 | `9.1` ↔ `10.1` |
| `filter_level` | 개별 행의 값 / 그룹의 집계값 | 집계 전 `WHERE` / 집계 후 `HAVING` | 7 | `23.1` ↔ `24.1` |

각 짝의 두 번째 레코드에는 `"contrast":{"kind":"boundary","paired_id":"9.1"}`처럼 첫 번째 레코드를 가리키는 정보가 있다. 두 레코드를 실제 스키마에 대응시킬 때에는 같은 테이블과 컬럼을 사용한다. 행·그룹 필터 대조에서 행의 값 태그와 `[AGG_VALUE, numeric, #1]`에는 같은 임곗값을 넣어야 필터를 적용하는 단계만 달라진다. 공통 필터·집계 함수·정렬과 수량을 조합한 대조 원본은 총 1,740쌍이다.

### 짧은 질문·날짜 정렬 추가 전후

일반 조회 비율을 고정하기 전에 비교한 두 파일은 seed 42, 질문 1,000건, 원본 334개다. 질문 안의 태그는 각각 한 단어로 센다.

| 지표 | 표현 확장 전 | 표현 확장 후 |
| --- | ---: | ---: |
| 10단어 이하 질문 | 21 | 70 |
| 질문 길이 중앙값 | 32단어 | 27단어 |
| 서로 다른 질문 시작 두 단어 | 44 | 70 |
| 날짜 컬럼이 주 정렬 키인 질문 중 시간 순서 표현 사용 | 0/15 | 45/45 |
| 표본에 등장한 서로 다른 `LIMIT` 수량 | 9 | 46 |
| 단순 집계 레코드 | 247 | 253 |
| 대조쌍 레코드(양쪽 합계) | 108 | 108 |

`LIMIT`은 1~100의 정수를 지원한다. 일반·그룹 조회의 수량 조합은 1~10과 11~100으로 나누어 두 범위에 차례를 준다. 날짜 오름차순에는 `oldest first`, 내림차순에는 `newest first` 같은 표현을 쓰며 날짜가 보조 키일 때에도 방향을 유지한다.

이전 자동 배분 설정의 50만 건 배분을 seed 42로 계산하면 단순 집계는 약 25%, 대조 레코드는 약 11.1%다. 회귀 테스트에서는 실제 대조 후보와 배분 순서를 사용하고 각 묶음의 크기만 세므로 50만 건의 파일을 생성하지 않는다. 상한을 명시하면 그 값이 비율보다 우선한다. 예를 들어 `--max-questions-per-sql 3`에서는 단순 집계 4,540개로 최대 13,620건을 만들 수 있다. 고정 비율을 사용할 때에는 할당량을 충족할 수 있는 상한이 필요하다.

## 대조쌍을 도입하기 전의 분포

아래는 seed 42로 SQL 구조 선택 방식과 일반 질문 틀을 차례로 변경했을 때의 기록이다. 두 파일 모두 질문 1,000건, 원본당 최대 3건이었다. 서로 다른 SQL은 두 파일 모두 334개로, 일반 조회 84개, 집계 84개, 그룹 조회 83개, 스칼라 서브쿼리 83개였다.

**일반 조회 원본 84개.** 각 칸은 기존 건수 → 새 건수다. `IN` 목록과 `BETWEEN` 범위는 각각 조건 하나로 센다.

| WHERE 조건 수 | 정렬·LIMIT 모두 없음 | LIMIT만 | 정렬만 | 정렬과 LIMIT 모두 |
| ---: | ---: | ---: | ---: | ---: |
| 0 | 0 → 4 | 0 → 6 | 0 → 5 | 3 → 6 |
| 1 | 0 → 6 | 0 → 5 | 2 → 5 | 6 → 5 |
| 2 | 0 → 5 | 0 → 6 | 3 → 5 | 22 → 6 |
| 3 | 0 → 5 | 0 → 5 | 5 → 5 | 43 → 5 |
| 합계 | 0 → 20 | 0 → 22 | 10 → 20 | 74 → 22 |

그룹 조회에서는 `ORDER BY` 사용이 72개에서 41개, `LIMIT` 사용이 78개에서 42개로 바뀌었다. 전체 12가지 조합 중 관측된 조합은 7가지에서 12가지로 늘었다.

| SQL 유형 | 행 조건 0개 | 1개 | 2개 | 3개 | 4개 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 집계 | 6 → 7 | 24 → 38 | 54 → 39 | — | — |
| 그룹 | 4 → 27 | 21 → 28 | 58 → 28 | — | — |
| 스칼라 서브쿼리 | 1 → 10 | 8 → 18 | 22 → 27 | 27 → 18 | 25 → 10 |

집계의 행 조건 0개 원본은 가능한 SQL 7개를 모두 사용했다. 그룹의 `HAVING`은 행 조건 수에서 제외했다. 서브쿼리 행은 안팎의 일반 필터 수를 더한 값이며, 집계 결과와 비교하는 필수 조건은 제외했다.

**표현 목록을 확장하기 전의 질문 1,000건.** 아래 두 행은 각 유형에 틀이 5개씩 있었을 때 측정한 결과다. 틀 번호는 각 유형의 `mappings.json` 목록 순서다.

| 질문 틀 | 1번 | 2번 | 3번 | 4번 | 5번 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 기존 | 334 | 333 | 333 | 0 | 0 |
| 변경 후 | 205 | 196 | 192 | 198 | 209 |

이때 `LIMIT`이 있는 질문에서 실제로 쓰인 ‘질문 틀 번호 × 건수 제한 표현 번호’ 조합은 3가지에서 15가지로 늘었다.

**일반 질문 틀을 65개로 확장한 시점.** 일반 컬럼 조회·전체 컬럼 조회·집계·그룹·스칼라 서브쿼리에 각각 13개씩 등록했다. 예를 들어 스칼라 서브쿼리는 행의 값을 기준값과 비교하는 질문과, 기준값을 먼저 설명한 뒤 어느 행을 반환할지 묻는 질문을 모두 생성한다. `LIMIT` 표현은 9개이며 수량이 1일 때는 `1 result`, 여러 개일 때는 `2 results`처럼 쓴다.

같은 seed 42로 다시 만든 1,000건에서 원본 SQL 334개와 ID를 대조했다. 65개 틀이 모두 등장했고, 621건은 새로 추가한 틀을 사용했다. 질문 틀과 하위 구절을 합친 등록 표현 342개 중 340개가 실제로 쓰였다. `LIMIT`이 있는 질문에서는 13개 틀 번호와 9개 건수 제한 표현으로 가능한 117가지 조합 중 110가지가 등장했다.

## 팀원 3에게 전달하는 JSON

파일은 UTF-8 JSON 배열이며 모든 원소가 `id`, `input`, `output` 문자열을 갖는다. 대조쌍의 두 번째 원소에는 `contrast` 객체가 추가된다. 일반 레코드 예시는 다음과 같다.

```json
{
  "id": "1.1",
  "input": "show {*} from <TABLE1>.",
  "output": "SELECT {*} FROM <TABLE1>"
}
```

- `id`의 두 번호는 각각 원본 SQL 번호와 그 SQL을 묻는 질문 번호다. 두 번호 모두 1부터 시작한다. 팀원 3은 스키마 매핑마다 부모 ID에 `.1`, `.2` 등을 붙인다. 후속 분할은 같은 생성 파일의 원본 번호를 기준으로 하고, 학습용 대조쌍은 `paired_id`로 연결된 두 원본을 함께 학습에 배정한다. 다른 seed나 SQL 틀로 새 전달본을 만들면 그 전달본의 ID로 후속 데이터를 연결한다.
- `input`은 팀원 3이 실제 스키마에 매핑할 영어 태그 질문이다. 컬럼은 질문의 첫 등장 순서대로 번호를 받는다. 같은 번호는 질문 전체와 SQL에서 같은 컬럼을 가리킨다.
- `output`은 뒷모델의 정답 SQL이다. 최종 조회식은 `{...}`, 일반 컬럼 참조는 `<...>`, 조건값은 `[...]`로 표시한다. 문자열·날짜 값에는 SQL 작은따옴표가 붙고 숫자 값은 그대로 들어간다. `LIMIT`은 질문에 있는 정수를 쓴다.

질문의 자연어는 문장 첫 글자까지 모두 소문자로 쓴다. SQL 키워드·함수와 태그 식별자(`TABLE1`, `COL1`, `AGG_VALUE`)는 대문자이고, 태그 안의 타입명(`numeric`, `string`, `date`)은 소문자다.

팀원 3은 `AVG`·`SUM` 및 숫자 `MIN`·`MAX`의 인자를 v1 스키마의 가격·재고·주문 수량에, 날짜 `MIN`·`MAX`의 인자를 주문 날짜에 연결한다. 서브쿼리의 안쪽과 바깥쪽에서 같은 값 태그를 사용하면 같은 값으로 복원한다.
